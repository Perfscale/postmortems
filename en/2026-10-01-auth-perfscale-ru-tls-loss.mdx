# Postmortem: TLS certificate loss on auth.perfscale.ru after Nginx Proxy Manager recreate

## Summary

While enabling HTTP/3, the Nginx Proxy Manager (NPM) container on the ru VPS
was recreated. During the recreate, NPM's `database.sqlite` was replaced by a
fresh empty file: the Let's Encrypt certificate binding for the
`auth.perfscale.ru` proxy host was lost, and the host started serving an old
custom certificate (`CN=www.perfscale.ru`, no auth in SAN). Client TLS
validation failed, and logins to the .ru control plane were broken for
~21.5 hours.

**Severity**: high
**Duration**: ~21.5 hours (2026-10-01 09:45 UTC → 2026-10-02 07:07 UTC)
**Impact**: new logins on .ru impossible; active sessions and the sites themselves unaffected

## Impact

- **Services affected**: auth.perfscale.ru (Keycloak), login on
  app.perfscale.ru / controlplane .ru
- **User impact**: users could not log in on the .ru domain — browsers aborted
  the TLS handshake (`no alternative certificate subject name matches target
  host name 'auth.perfscale.ru'`). Existing sessions kept working, and
  perfscale.ru / app pages served normally
- **Business impact**: degraded sign-in to the product on the primary domain;
  no data loss
- **Detection time**: ~5-6 hours (incident from 09:45 UTC, found during manual
  post-deploy checks the same day; there is no certificate-validity alerting)

## Root Cause

1. HTTP/3 required publishing `443/udp`, so the NPM container was recreated
   (`docker compose up -d --force-recreate` or equivalent).
2. After the recreate, the NPM backend hung on startup (IP Ranges fetch →
   admin API 502, unhealthy); fixed with `docker restart`.
3. Meanwhile `database.sqlite` in the `/data` volume turned out to be a fresh
   file created at 09:45 UTC. The proxy host configuration in the DB survived
   (was restored/matched), but the Let's Encrypt directory and the certificate
   binding for `auth.perfscale.ru` did not. Why the old file/volume was absent
   at startup is **undetermined** (volume mapping not yet investigated).
4. In this state NPM fell back to serving the only available custom
   certificate npm-6/7 (`CN=www.perfscale.ru`, SAN: www/autodiscover/mail/
   owa/perfscale.ru — "Exchange-style"), which does not cover
   auth.perfscale.ru.

### Contributing Factors

- NPM state (sqlite + `/data/letsencrypt`) lives in a single volume with no
  backups; container recreate is a manual operation without a checklist.
- No TLS certificate validity monitoring (blackbox probe) — detection was
  manual only.
- NPM's default email `admin@example.com` — Let's Encrypt refuses to register
  an ACME account for example.com, which blocked the first reissue attempt
  (HTTP 500 from the NPM UI) and added delay.
- The presence of a "similar-looking" custom certificate npm-6 created a false
  repair path (selecting it manually instead of issuing a new LE cert).

## Resolution

- **Immediate mitigation**: issued a new Let's Encrypt certificate for
  auth.perfscale.ru via the NPM UI (Proxy Hosts → auth.perfscale.ru → SSL →
  Request a new SSL Certificate → real email → Force SSL). The HTTP-01
  challenge passed automatically (the host's port 80 was listening and
  proxying).
- **Permanent fix**: a valid LE certificate is in place; NPM auto-renewal is
  expected to pick it up (verify within 30-90 days).
- **Verification**: `curl https://auth.perfscale.ru/` → 200; LE chain valid;
  `…/realms/perfscale/.well-known/openid-configuration` → 200; SAN contains
  only auth.perfscale.ru.

## Lessons Learned

### What Went Well

- The HTTP-01 path was alive (port 80 proxied), so reissuing the certificate
  took minutes once the email problem was fixed.
- The proxy host configuration survived in the DB — routes did not need
  rebuilding, only the certificate.
- NPM logs quickly localized the 500 cause (ACME email).

### What Went Wrong

- A stateful container was recreated without a backup and without verifying
  the volume — certificates were lost silently.
- No TLS alerting: the login breakage was found by chance, hours later.
- The default `admin@example.com` email blocked the first reissue attempt.
- The "pick a similar-looking cert" attempt (npm-6) wasted time — its SAN
  does not cover auth.perfscale.ru.

### Where We Got Lucky

- Only the auth host broke; the main site and gateway kept working.
- Active user sessions were not invalidated — only new logins were affected.
- The HTTP/3 config (the quic advanced_config) survived the recreate because
  it lives in the same proxy hosts DB.
